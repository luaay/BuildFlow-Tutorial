# BuildFlow --- Episode 08

## MediatR & Domain Events: Licensing, Integration, and IDomainEvent

> هذه الوثيقة هي دليل التنفيذ العملي المرتبط بالحلقة الثامنة من سلسلة
> BuildFlow. المرجع الأساسي لهذه الخطوات هو مرجع بناء الجزء السابع:
> اختيار مكتبة المراسلة وعقد الحدث.

------------------------------------------------------------------------

## 1. هدف الحلقة

في هذه الحلقة ننتقل من قرار اختيار مكتبة المراسلة إلى تطبيقه داخل مشروع
`SharedKernel`.

سنقوم بـ:

1.  مراجعة وضع ترخيص `MediatR`.
2.  اختيار الخيار المناسب لمشروع BuildFlow.
3.  تثبيت `MediatR` داخل `SharedKernel`.
4.  تنفيذ `dotnet build` للتحقق من نجاح الإضافة.
5.  إنشاء عقد `IDomainEvent`.
6.  إضافة `EventId`.
7.  إضافة `OccurredOnUtc`.
8.  ربط `IDomainEvent` مع `INotification`.
9.  فهم المفاضلة المعمارية الناتجة عن هذا الربط.

------------------------------------------------------------------------

## 2. قرار استخدام MediatR

تحوّلت `MediatR` إلى نموذج ترخيص مزدوج في منتصف عام 2025.

الإصدارات الجديدة تصدر تحت رخصة مجتمعية ورخصة تجارية، مع وجود إصدار
مجتمعي مجاني للحالات التي يشملها ذلك النموذج، كما تبقى الإصدارات الأقدم
تحت رخصتها المفتوحة الأصلية.

بالنسبة إلى BuildFlow، وهو مشروع تعليمي وشخصي، يقع الاستخدام ضمن الإصدار
المجتمعي المجاني وفق المرجع.

### الخيارات الثلاثة

عند مواجهة مكتبة غيّرت ترخيصها، توجد ثلاثة خيارات:

1.  استخدام الإصدار الحديث تحت الرخصة المجتمعية.
2.  تثبيت آخر إصدار بقي تحت الرخصة المفتوحة القديمة.
3.  استخدام بديل مفتوح بالكامل.

في BuildFlow اخترنا الخيار الأول، لأن `MediatR` ما زالت مطلوبة بالاسم في
كثير من إعلانات الوظائف، ولأن الاستخدام التعليمي والشخصي للمشروع يقع ضمن
الإصدار المجتمعي المجاني.

> Engineering Tip:
>
> قبل اعتماد أي مكتبة أساسية، تحقّق من وضع ترخيصها الحالي، ولا تعتمد على
> معلومات قديمة عنها.

------------------------------------------------------------------------

## 3. تثبيت MediatR داخل SharedKernel

بما أن عقد `Domain Event` سيرتبط بالمكتبة، نضيف `MediatR` إلى مشروع
`SharedKernel`.

نفّذ الأمر التالي من جذر الحل:

``` bash
dotnet add src/SharedKernel/BuildFlow.SharedKernel.csproj package MediatR
```

بعدها نفّذ:

``` bash
dotnet build
```

الهدف من `dotnet build` هو التأكد من أن المشروع ما زال يُبنى بنجاح بعد
إضافة الحزمة الجديدة.

قد تظهر أثناء البناء رسالة معلوماتية تتعلق بالترخيص. وفق المرجع، هذه
الرسالة لا تمنع المشروع من البناء أو التشغيل بشكل طبيعي.

------------------------------------------------------------------------

## 4. إنشاء IDomainEvent

أنشئ الملف:

``` text
src/SharedKernel/Domain/IDomainEvent.cs
```

ثم ضع الكود التالي:

``` csharp
using MediatR;

namespace BuildFlow.SharedKernel.Domain;

// عقد لكل شيء مهم حدث في النطاق، بصيغة الماضي
public interface IDomainEvent : INotification
{
    Guid EventId { get; }            // لدعم منع التكرار
    DateTime OccurredOnUtc { get; }  // توقيت الحدوث بالـ UTC
}
```

------------------------------------------------------------------------

## 5. لماذا Interface؟

تم إنشاء `IDomainEvent` كـ `Interface` وليس `Class` لأنه يمثل عقداً وليس
كائناً سيتم استخدامه مباشرة.

أي `Class` أو `Record` يمكنه تطبيق هذا العقد.

بهذا نحدد القواعد المشتركة لأحداث النطاق من دون فرض أسلوب تنفيذ معين على
الأحداث نفسها.

------------------------------------------------------------------------

## 6. لماذا ترث IDomainEvent من INotification؟

السطر:

``` csharp
public interface IDomainEvent : INotification
```

هو الرابط بين عقد أحداث النطاق و`MediatR`.

بهذا يصبح كل `Domain Event` يطبق `IDomainEvent` قابلاً للنشر من خلال
`MediatR`، ويمكن ربطه بالمعالجات المناسبة عند نشر الأحداث.

------------------------------------------------------------------------

## 7. EventId

الخاصية:

``` csharp
Guid EventId { get; }
```

تمثل الهوية الفريدة للحدث.

كل حدث يحصل على معرف مختلف، حتى لو كان من النوع نفسه.

وجود `EventId` مهم في حالات تكرار إرسال أو معالجة الحدث، لأنه يسمح
بالتعرف على الحدث نفسه ودعم منع معالجته أكثر من مرة.

------------------------------------------------------------------------

## 8. OccurredOnUtc

الخاصية:

``` csharp
DateTime OccurredOnUtc { get; }
```

تسجل وقت حدوث الحدث.

نستخدم `UTC` بدلاً من الوقت المحلي لأن الأنظمة الحديثة قد تعمل في أكثر من
منطقة زمنية.

استخدام مرجع زمني موحد يجعل مقارنة الأحداث وترتيبها أكثر وضوحاً، ثم يمكن
تحويل الوقت إلى التوقيت المحلي عند عرضه للمستخدم.

------------------------------------------------------------------------

## 9. لماذا IDomainEvent بدلاً من INotification مباشرة؟

وجود واجهة `IDomainEvent` يعطي المشروع اسماً دلالياً يعبر عن مفهوم من
مفاهيم النطاق.

بدلاً من أن يتعامل كود المشروع مع اسم تقني قادم من مكتبة خارجية، يتعامل
مع مفهوم واضح:

``` text
Domain Event
```

كما يسمح ذلك بالتعامل مع جميع أحداث النطاق باعتبارها نوعاً واحداً،
وتمييزها عن أي إشعارات أخرى قد تُستخدم داخل التطبيق لاحقاً.

------------------------------------------------------------------------

## 10. المفاضلة المعمارية

هناك نقطة معمارية مهمة في هذا التصميم.

بما أن:

``` csharp
IDomainEvent : INotification
```

فإن `SharedKernel` أصبح يعتمد على مكتبة `MediatR`.

وبالمعنى الصارم جداً لـ `Clean Architecture`، توجد هنا تبعية من النطاق
إلى مكتبة خارجية.

هذا القرار تم اختياره في BuildFlow عن وعي.

البديل الأكثر صرامة هو إبقاء واجهة الحدث نقية بلا تبعية، ثم استخدام طبقة
إضافية لربط النوع الداخلي بنوع الإشعار الخاص بمكتبة المراسلة.

لكن هذا البديل يضيف تعقيداً لا يبرّره حجم المشروع في سياق BuildFlow.

الهدف ليس تطبيق كل قاعدة بصورة حرفية، بل فهم المبدأ واختيار المفاضلة
المناسبة للسياق.
